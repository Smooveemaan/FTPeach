# The vault is FTPeach's own file, not a Stronghold snapshot

Up to 0.5 the vault's secrets were a Stronghold snapshot. FTPeach used it as an encrypted key-value store and nothing more: none of its protected-memory records, procedures or sync. For that it brought libsodium, a native library that had to be downloaded, checked and linked by hand on every machine and runner, an unmaintained `bincode` and `paste`, and a separate build per operating system to port. The master password never reached Stronghold anyway: Argon2id and XChaCha20-Poly1305 in FTPeach already wrapped the random data key that opened the snapshot.

So `vault.dat` is that data key sealing the secrets with XChaCha20-Poly1305, a format version in front, rewritten whole through an atomic replacement, held in memory as zeroizing buffers while the vault is open. `vault.json` and the Windows Hello credentials did not change, since they wrap the same key. A vault of 0.5 moves at its first unlock: a small reader of the one snapshot shape FTPeach wrote (age with scrypt, LZ4, bincode) takes the secrets out, and the snapshot stays beside the new file as `vault.hold.backup`. The reader goes once no supported version can still find a `vault.hold`; that is decided in 0.7.x. An earlier FTPeach cannot open a moved vault, which is why the change shipped as 0.6.0.
