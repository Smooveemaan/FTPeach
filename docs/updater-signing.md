# Signing Tauri updates

Updater artifact signatures protect FTPeach updates from substitution. This is not Windows Authenticode: without a separate code-signing certificate, SmartScreen may still warn about an unknown publisher. [release-trust.md](release-trust.md) separates the two and describes key rotation.

## Unix packages in development

The unreleased macOS/Linux updater uses the plugin's native `install` method
after FTPeach verifies the saved bytes again. It obtains a fresh server offer
before installation, requires its version and signature to match the saved
manifest, and passes the verified memory buffer to the plugin. Network errors
leave the package waiting and the application running; a successful response
that removes or replaces the offer discards that download. See
[the decision](adr/0009-unix-updates-require-a-current-offer.md).

Anti-rollback reads the version from the signed package itself: macOS uses
`FTPeach.app/Contents/Info.plist`, Debian uses `Version` in the gzip-compressed
`control` archive generated by Tauri, and an ELF64 type-2 AppImage uses the
`ftpeach-update-version` resource inside its SquashFS. `build.rs` generates this
resource from the Cargo package version before bundling. Missing, ambiguous or
mismatched versions are refused, as are versions no newer than the running build.
No downloaded package is executed to discover its version.

The AppImage reader supports gzip, xz and Zstandard. The optional Zstandard
feature of the SquashFS reader remains disabled because it pins vulnerable
versions; its supported codec hook uses the fixed Zstandard library instead.
All dependency advisory checks remain blocking, without new exceptions.

The startup request runs in the background. If a connection, transfer or edited
external file is already active when it completes, installation waits for the
user or the next launch. Installation follows orderly shutdown and requests a
restart. An unsuccessful installation is recorded so it cannot repeat on every
launch. These paths have automated parser, signature and server-response tests;
native installation and restart still need acceptance on each target OS.

## Keys

`src-tauri/tauri.conf.json` contains only the public key. Never store the private key or its password in the repository, `.env`, release artifacts, or CI logs. Losing the private key prevents existing installations from accepting updates signed by a new pair, so keep a separate backup in secure storage.

Generating a pair is needed only to rotate the key; follow the rotation order in [release-trust.md](release-trust.md#the-updater-private-key), because installations accept only updates signed for the public key they already have:

```powershell
npm run tauri -- signer generate --write-keys C:\secure\ftpeach-updater.key
```

The command creates a private file and a public file with a `.pub` suffix. Put the `.pub` contents in `plugins.updater.pubkey`; store the private file in a secret manager and separate secure backup. Keys under `test/fixtures/updater/` are test-only and must never sign releases.

## GitHub Actions

Create these secrets in the GitHub `release` environment:

- `TAURI_SIGNING_PRIVATE_KEY`: the complete production private-key contents;
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: the key password.

Restrict `release` to exactly the `master` deployment branch, without required
reviewers. Keep signing secrets at environment scope. The separate `release-tag`
environment requires the owner's approval and disallows administrator bypass.
The workflow reads the actual settings before signing or deploying and fails
closed when they differ ([release-trust.md](release-trust.md)).

A push of `master` whose last commit contains the exact line `Release-Check: true`
runs full public and closed checks, then calls `.github/workflows/release.yml`
in the same CI run. It builds and signs Windows NSIS and portable packages,
verifies every updater signature, and retains the exact files before attestation
and package acceptance. Signing never exposes the key to acceptance runners.

After automatic and recorded manual acceptance, one protected deploy approval
permits an annotated application tag and a draft. The finalizer resumes missing
uploads, rejects conflicting files and verifies the downloaded draft and feed.
The draft includes the installer, portable ZIP, `latest.json`, audit archive,
candidate manifest and verification record. Signatures are carried in the feed.
The owner publishes the draft and checks real updates from the public feed.
Tags never start another build. See [release recovery](release-trust.md) for
retained candidates; a failed checker does not require rebuilding their bytes.

Run a local signed build only in the current PowerShell session:

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = 'C:\secure\ftpeach-updater.key'
$signingCredential = Get-Credential -UserName 'updater-signing' -Message 'Updater key password'
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = $signingCredential.GetNetworkCredential().Password
try { npm.cmd run build:tauri }
finally {
  Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY
  Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD
  Remove-Variable signingCredential
}
```

Enter the password in the credential prompt, not as a literal command or command-line
argument, which can be saved in shell history or exposed in the process list. The
`finally` block removes this session's signing variables even when the build fails.
